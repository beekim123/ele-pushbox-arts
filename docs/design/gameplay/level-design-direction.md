# 关卡设计新方向（草案）：一条可重复的关卡生产线

状态：草案（概念设计）；新关卡线的设计以美术仓库 `docs/design/gameplay/` 为准（用户 2026-10-23 决定）；实现以后在游戏仓库开新分支做，现在只做设计。
日期：2026-10-23　　来源：用户与 Claude 的多轮讨论　　仓库事实核对基线：`1ad39f6`
范围：只谈**关卡设计**。配送规则重设计、剧情融合、工作包与分支流程不在本文件内（见第 12 节）。

## 0 一页纸（先看这里）

**要解决的问题**：现在的关卡模式更像"机制演示"，没有"想通了"的乐趣（数据见第 1 节）。

**新思路**：把"做关卡"变成一条能反复使用的生产线——

```
机制清单 → 排列组合（机制对 + 冲突）→ HTML 设计器里摆放 → 求解器 + 难度评分
        → 配上风格 → 真人试玩校准 → 导出 JSON（进 git）→ Godot 读取
```

| 项 | 状态 |
|---|---|
| 每个关卡独立设计；形态有单屏、大地图、多屏联动 | 已定 |
| HTML 设计器：网页里拖拽搭图，**导出 JSON，Godot 写加载逻辑直接读，JSON 提交 git**（不做本地服务，以后可加） | 已定（用户 2026-10-23） |
| 机制：只列清单（现有 + 以后可加），**不做选择** | 已定（概念阶段） |
| 操作：动作键 + 方向，一关最多 2 个工具 | **暂定**，实机可能改 |
| 联动：信号联动 + 多个单屏，不做超大物理世界 | **暂定**，实机可能改 |
| 难度：自动指标 + 设计者标注 + 真人校准，先做指标面板 | 建议 |
| 风格：机制先行，皮肤后上，规则与皮肤分两层 | 建议 |
| 模块归属、候选机制、难度权重、JSON 细节 | 待定（第 11 节） |

## 1 为什么要改（现状诊断）

灵感来自《沉星之序》（Jonathan Blow）：规则套数少、把组合挖到底、关卡一眼读得懂、没有文字教学、删掉"不重要也不精彩的难度"。对照之下，现在的关卡库是"机制很多、每个机制的谜题很少"。

**数据**（设计模型 `content/model-check.generated.json`，**不是 SDK 实测**）：

| 指标 | 数值 |
|---|---|
| 关卡数 | 46（基础 7 / 水 9 / 爆破 8 / 酸雾藤 9 / 冷热 7 / 实验 6） |
| 最短解步数 | 中位 9，范围 4–13 |
| 可达局面数 | 中位 71，范围 12–2413 |
| 局面数不到 100 的关 | 28 / 46 |
| 一个死局都没有的关（怎么走都不会错） | 12 / 46 |
| 用到的机制 | 36 个；19 个只出现在 1 关；平均每个机制 1.6 关 |

各章分布见附录 A。

**怎么理解这些数字**：

- 一关只有十几到几十个局面，靠撤销乱试几分钟就能把整关走遍，这是"演示"，不是"谜题"。
- 这是定位造成的：游戏仓库 `docs/design/game-design.md` 第 1、6.1 节把关卡模式定义成"每关只演示一个机制 + SDK 回归测试"；教学关的 `discovery` 写的是"机关怎么作用"（夯土能挖、箱子推上升降台再踩按钮）。
- 读规格的判断：最像谜题的是 E01–E06、G10、F09 这批跨章组合（有诱饵、有先后），但实验组默认是隐藏的（`controller.gd`：除非设置"开放全部关卡"或调试构建）。
- **形式检查救不了**：游戏仓库 `docs/design/level-quality.md` 的检查项（作者解与最短解差小于 2、死局大于 0、无捷径……）在 LV-05 的交付里都通过了，状态空间依然很小（实验组局面数中位 68）。所以验收要加两样东西：**删元素测试**和**真人试玩**。
- 现有 `reachable_states` 会被"背包里的沙可以随意倒"虚增（游戏仓库 `docs/design/game-design.md` 6.3 的说明），不能直接当难度用（见第 8 节）。

## 2 总体思路

### 2.1 生产线

| 环节 | 产出物 |
|---|---|
| 机制清单 | 每个机制一张"机制卡"（附录 C）：读什么、改什么、守恒还是一次性、验证等级 |
| 排列组合 | 一批"机制对"，每对配一个"冲突"，每对四关（引入、变化、转折、收束） |
| 设计器 | 地图、试玩、求解、SDK 提醒、难度面板、皮肤预览、导出 JSON |
| 求解器 + 难度评分 | 局面数、关键动作数、诱饵长度、删元素测试结果；1–5 星 |
| 风格 | 同一机制可配多个地区皮肤，换皮肤不改规则 |
| 真人试玩 | 3–5 个新玩家，记录表见附录 C |
| 导出 | 一关一个 JSON，提交 git，Godot 直接读 |

### 2.2 原则

1. **每关独立设计**：从一张"想法卡"开始（附录 C），不套模板、不批量填充。
2. **洞见代替演示**：每个非教学关写一句"玩家会先想____；这行不通，因为____；真正的做法是____。"写不出诱饵，就只能当教学关。
3. **冲突原则**：每个非教学关至少有一处"两件事抢同一份资源"——物质（沙、水的总量）、空间（一格宽、只能登一格）、一次性效果（桥塌、酸耗尽、引信烧完、冰融）。
4. **机制先行，皮肤后上**：先定这张图用哪几个机制，再选主题（第 9 节）。
5. **求解器 + 真人两道关**：求解器只和设计模型一样可信；好不好玩只有真人试玩能回答。
6. **暂定项不写死**：操作方案、联动方案以后实机可能改，所以数据格式不绑定它们（第 4、7 节）。

## 3 关卡形态（联动方案为暂定）

| 形态 | 是什么 | 现状 |
|---|---|---|
| 单屏 | 一屏（最大 20×10 格）一个谜题 | 已有 46 关 |
| 大地图 | 比一屏大，镜头跟随，几个小谜题共用同一份沙或水 | 配送房间设计过 1×1 到 2×2 屏（最大 40×20 格）；SDK 能否直接开这么大**未验证**（游戏仓库 `docs/design/mode-delivery.md` 第 6 节） |
| 多屏联动 | 这屏动、那屏变 | 没有 |

**暂定方案：大地图和联动都做成"几个单屏拼起来"，不做一个超大的物理世界。**

- 撤销需要保存世界状态；扩大物理世界会增加内存和性能成本，应另行评估（设计层面的估算，非实测）。
- 代价：沙和水**不能流过屏幕边界**；跨屏只靠"信号"（压板、开关、收集斗达标 → 另一屏的门、升降台、释放口）。
- 视觉上可以连续（镜头衔接），物理上是几个独立世界。
- 想要水真的流过屏幕，需要大世界，要另外评估性能和撤销。

**联动要防"软死局"**：在一屏做了不可逆的事，让另一屏再也过不去。需要全局撤销（所有屏一起回退），求解器也要专门查。

**结构参考"锁与钥匙"**：钥匙不一定是物品，也可以是"某个状态"（水位到了、压板被压住）。

**难度怎么算**：多屏关拆开算，每屏一个分，再加屏与屏之间的"接口"数（第 8 节）。

## 4 操作简化（暂定）

### 4.1 现状

玩法动词 7 个，按法见 游戏仓库 `docs/design/game-design.md` 第 2 节：

| 动作 | 现在的按法 |
|---|---|
| 走、推、登阶 | ← → 或 A D |
| 爬梯 | ↑ ↓ 或 W S |
| 挖 | Shift + 方向；或先按 X 再按方向；或鼠标左键点相邻格 |
| 倒沙 | Ctrl（Mac 为 ⌘）+ 方向；或先按 C 再按方向；或鼠标右键 |
| 放炸药 | B + 方向；或先按 B 再按方向；或把炸药图标拖到相邻格 |
| 拨开关 | 站在开关上按 ↑ |
| 系统键 | Z 撤销、R 重开、Tab 观察、H 提示、Esc 暂停 |

光是"教按键"就做了一整套引导（DSN-03、UX-04～UX-07），说明键位本身偏重。

### 4.2 暂定方案

**玩法键只留 6 个：方向键 4 个 + 动作键 1 个（空格）+ 撤销（Z）。** 重开 R、提示 H、暂停 Esc 当系统键。

| 键 | 作用 |
|---|---|
| ← → ↑ ↓ | 走、推、爬梯 |
| 空格 + 方向 | 对那个方向的相邻格使用"本关工具"，动词由目标格决定 |
| 站在开关上按空格 | 拨开关 |
| Z | 撤销 |
| Q（仅当本关有 2 个工具） | 切换工具 |
| 鼠标 | 点相邻格 = 空格 + 那个方向 |

**动词由目标格决定**（沿用现有限制：挖只能左、右、下，倒只能左、右）：

| 目标格 | 当前工具 | 动作 |
|---|---|---|
| 夯土或沙堆（左、右、下） | 铲 | 挖 |
| 空格（左、右），背包里有沙 | 铲 | 倒 |
| 相邻格（左、右、下） | 炸药 | 放炸药 |

**一关最多 2 个工具**，屏幕上显示工具图标。这也会逼关卡更聚焦。

一个组合键取代现在的 Shift、Ctrl（⌘）、B 三个修饰键，也不用再记"哪个键对应哪个动作"。

### 4.3 为什么以后改键位代价不大

- 关卡数据里不写按键。挖、倒沙、放炸药在作者解里本来就按"动作"记（`DIG_L`、`POUR_R`、`BOMB_D`……）。
- 拨开关目前记成 `U`，换方案时要改成一个动作记号，是个小改动。
- 键位映射应放在一张"动作 ↔ 按键"表里。

### 4.4 要验证

- 3 个新玩家，不教，10 分钟内能不能自己发现"空格 + 方向"（暂定：至少 2 人）。
- 备选 A：点击优先（鼠标或触屏点相邻格），键盘仍可用。
- 备选 B："撞什么做什么"（走进夯土就挖）。**不推荐**：能登上去的一格土会有歧义（登阶规则优先于挖）。

### 4.5 并入时要同步

游戏仓库 `docs/design/onboarding.md` 和 UX-04～UX-07 的键帽提示、"操作说明"页、M03/M04 的教学提示、设置里的"重看引导"。

### 5.5 SDK 事实限制（设计时要记住）

- 反应、点燃、相变、寿命到期**都没有事件**，只能固定阶段后轮询；温度变化不进入"静止判定"。
- 开阔地上一格沙会摊成坡；整格沙谜题要靠墙或落进坑里。
- 爆炸不被墙挡，只看距离和抗爆性；附近的可燃物可能被点燃。
- 气压只推气体和粒子，不推箱子、粉末、液体。
- 含刚体的世界从快照载入后不保证位级一致，撤销只能从开局重放。
- 有电源时世界永远静不下来，只能固定阶段。

### 5.6 观察

- 已实现的 36 个里，真正"有 SDK 味道又足够确定"的是 B 级那一小撮（沙、水、挖、浮沉、收集斗……）；C 级最多，也最难验证。
- 未实现的 41 个里，有 9 个是为怪物和动物准备的（配送用），不一定适合纯解谜。

## 6 排列组合：怎么用机制组成谜题

### 6.1 按"机制对"设计，不按"机制"设计

每个机制先写一张机制卡（附录 C）。示例：

| 机制 | 读什么 | 改什么 | 性质 |
|---|---|---|---|
| 挖/倒沙 | 地形 | 取走/放下一格；背包 | 守恒（沙的袋数） |
| 水 | 开口、容器、沙 | 水位 → 箱子的高度 | 守恒（水量） |
| 木/铁箱 | 水位、地形 | 位置、压板、桥载重 | 木浮铁沉 |
| 压板 + 门/开关 | 重量 | 门、机关 | 可锁存或不锁存 |
| 收集斗/升降台 | 材料量 / 触发 | 点灯 / 位置 | 一次性 |
| 承重桥 | 重量 | 桥塌 | 一次性 |
| 支撑/下落 | 支撑格 | 物体下落 | 不可逆 |

### 6.2 三步法

1. **找有"接口"的对**：一个机制的输出正好是另一个的输入，例如沙 → 水位 → 箱子高度 → 压板。
2. **给每对加一个冲突**：两件事抢同一份资源。
   - 物质：沙、水的总量。
   - 空间：一格宽、只能登一格、不推箱链。
   - 一次性：桥塌、酸耗尽、引信烧完、冰融。
3. **四关结构**：引入（安全地看懂，可以没有死局，但仍要有发现）→ 变化 → 转折（拧上第三个机制，出现诱饵）→ 收束（组合，本组最难）。这和马里奥 3D World 的"起承转合"、游戏仓库 `docs/design/level-quality.md` 第 3 节的一章结构一致。

### 6.3 预算（粗算）

8 个核心机制有 28 对；挑 15–20 对有接口的，每对 3–4 关，约 50–80 关。

### 6.4 机关积木

设计器的调色板里，除了单格，放预制的小模块：压板 + 门、一口井 + 浮箱、一座桥 + 深坑……整块拖进地图，再改尺寸、接线。积木就是"机制对"的最小实现。

### 6.5 不自动生成

难度控制是 Sokoban 生成器公认的难点（多个子目标互相影响，不能靠堆子目标调难度）。先手工做到 50 关以上，再谈生成。

## 7 HTML 地图设计器

### 7.1 它是什么

一个网页：左边是调色板（岩石、土、沙、水、箱子、门、压板……），右边是网格。把东西拖进去就搭出一张谜题地图，还能当场试玩、让电脑算有没有解、算难度，最后导出一个 JSON。它是做关卡的工具，不是游戏本身。

放在作者页面（`tools/authoring`，游戏仓库，私有）。设计模型 `tilemodel.js` 本来就是 JS：作者页面已能回放作者解（`scenes.js`），配送房间页已能键盘试玩（`rooms2.js`），设计器可以直接复用。

### 7.2 工作流

```
画 → 试玩 → 求解 → 看 SDK 提醒 → 看难度面板 → 导出 JSON → 放进仓库 → 提交
```

### 7.3 功能

**最小可用版（单屏）**

- **画**：调色板（图例见 游戏仓库 `docs/design/game-design.md` 6.5）；拖拽、刷子、框选、镜像；机关弹出配对（同符号的门和压板、成对传送阵、桥的承重）。
- **机关积木**：见 6.4。
- **试玩**：同屏键盘试玩 + 撤销。
- **求解**：实时显示有解 / 无解 / "太大算不完"；最少步数；局面数；死局数；作者解回放。
- **SDK 提醒**：把踩过的坑变成实时提示（7.5）。
- **删元素测试**：自动逐个删掉地图里的元素，删了谜题还成立，说明它是凑数的。先例：配送房间检查已有"必需机制"检查（把 `requires` 里的机制冻结后再搜一次，必须走不通，见 `check-rooms2.mjs`），删元素测试是把它从"机制"推广到"每个元素"。
- **诱饵回放**：按 `decoys` 回放诱饵，核对它合法且走进死局或浪费。
- **难度面板**：第 8 节。
- **皮肤预览**：换主题不改规则（第 9 节）。
- **导出**：见 7.4。

**之后**：多屏（每屏一个标签页 + 联动编辑）、大地图（可滚动画布）。

**提醒**：求解器只和设计模型一样可信，B、C 级机制的结果要标"需 SDK 核对"。

### 7.4 导出 JSON 与 Godot 读取（用户已定）

**决定**（用户 2026-10-23）：设计器里操作完成后，**导出一个 JSON 文件**；Godot 侧写加载逻辑**直接读这个 JSON**；这个 JSON **提交进 git**。不做"本地小服务"（以后觉得手动搬运麻烦再加，格式不变）。

**现有链路**（2026-10-23 核对，新方案沿用）：

```
关卡规格 JSON（content/levels/<模式>/<组>/<编号>.json，格式 pushbox.levelspec/1）
  → compile_content.gd 编译 → game/generated/content/levels/...
  → Godot 通过 res://generated/content-manifest.json 读取
```

也就是说"JSON 直接给 Godot 用"在现有工程里本来就是这么做的；设计器只是把"手写 JSON"换成"画出来再导出"。

**格式原则**（草案）：

1. **一关一个文件，人能读、能 diff**：地图用字符串数组，缩进 2 空格，UTF-8，末尾换行；键顺序沿用现有关卡文件（`format`、`id`、`chapter`、`mode`、`group`、`mechanisms`、`order`、`title`、`role`、`teaches`、`requires`、`discovery`、`map`、`links`、`devices`、`bag`、`solution`、`hints`、`misreads`、`sdk`、`checks`），新字段接在后面。
2. **导出必须确定**：同一关反复导出，字节完全相同；文件里没有时间戳、随机数。否则 git 记录里全是噪音。
3. **作者写的和工具算的分开**：关卡文件只放作者写的内容；求解器结果、难度指标、评分放生成文件（沿用 `content/model-check.generated.json` 的做法）。
4. **向后兼容**：`pushbox.levelspec/1` 的 46 个现有关卡不用迁移；新格式暂名 `pushbox.levelspec/2`，是 `/1` 的超集，新字段都可选。
5. **Godot 只需要一个加载器**：读 JSON → 建关卡会话，不关心是哪个工具画的。运行时真正需要支持的新字段只有 `tools`、`skin`、`zones`、`signals`；`insight`、`conflict`、`decoys`、`design_difficulty` 只给作者工具用。加载器对未知字段是忽略还是报错，并入时核对。
6. **同一份格式说明，三处校验**：设计器导出前、`content.mjs check`、Godot 加载时。是否用 JSON Schema，待定。

**拟增字段**（`/2`，全部可选）：

| 字段 | 谁写 | 作用 |
|---|---|---|
| `format` | 工具 | `pushbox.levelspec/2`；`/1` 文件继续有效 |
| `insight` | 设计者 | 洞见句三段：`first_instinct`、`why_not`、`real_move` |
| `conflict` | 设计者 | 冲突来源，数组：`matter`、`space`、`one_shot` |
| `tools` | 设计者 | 本关的主动工具，最多 2 个：`shovel`、`bomb`（开关不算） |
| `decoys` | 设计者 | 诱饵回放列表：`name`、`moves`（动作记号）、`ends`（`dead` 或 `waste`） |
| `skin` | 设计者 | `theme`（主题编号，如 `theme.ruins`），可选 `variant`；不改规则 |
| `design_difficulty` | 设计者 | 自评 1–5，只用于和计算值、真人数据对照校准 |
| `zones` | 设计者 | 多屏：每屏 `id`、`map`、`devices`、`links`（屏内）；单屏关不写，顶层 `map` 仍有效 |
| `exits` | 设计者 | 屏与屏之间的通行连接（梯子、门、洞口）：`from`、`to` |
| `signals` | 设计者 | 跨屏联动：`from`（屏、设备）→ `to`（屏、设备）、`kind` |

**设备要有稳定的 id**：现有设备靠序号互相引用（例如 `"trigger": {"device": 0}`）。单屏够用；跨屏联动需要稳定 id，设计器导出时给每个设备生成。

**一次导出的完整流程**：

1. 设计器里画、试玩、看求解结果和提醒。
2. 点"导出"：浏览器下载 `<关卡编号>.json`。
3. 放进 `content/levels/<模块>/<组>/`。按 游戏仓库 `AGENTS.md` 2b，关卡里的 `mode`、`group`、`mechanisms` 必须和关卡计划（`content/catalog/groups.json`）一致，所以新关要先在计划里登记（现在由设计包改；并入时核对能否简化）。
4. 跑内容检查与编译（`compile_content.gd`）；Godot 读生成的内容清单。
5. 提交：关卡 JSON 进 git；求解器、难度结果是生成文件。
6. 示例见附录 B。

### 7.6 要避免的坑

- 设计器容易越做越大：先守住最小版（单屏的画 + 试玩 + 求解 + 提醒 + 导出）。
- 求解器"太大算不完"是常态（多屏尤其），界面要有这个状态，不能卡死。

## 8 难度评分

**共识：没有真人数据的综合分数就是拍脑袋。** 所以分三层，先出指标面板，等有真人数据再合成总分。

### 8.1 第一层：自动指标（求解器）

| 指标 | 白话 | 现有数据能否直接给 |
|---|---|---|
| 关键动作数 | 只数推、挖、倒、拨、放，把走路折叠掉 | 否；现有 `shortest` 含走路 |
| 机制种数 | 解里必须用到的机制 | 否；配送房间检查已有"冻结某个机制再搜一次"（`check-rooms2.mjs`），关卡检查（`check-levels.mjs`）还没有，要新增 |
| 局面数 | 折叠走路后数"箱子和地形的布局 + 人能到的区域"，不数人站哪格 | 否；现有 `reachable_states` 含走位和背包自由倒沙，偏大 |
| 诱饵长度 | 第一直觉能走几个动作才走死 | 需要 `decoys` 字段 |
| 联动数 | 因果跨屏或跨远距离的条数 | 多屏才有 |
| 剩余元素数 | 删元素测试后剩下的元素 | 否 |

学术依据：Jarušek & Pelánek 对 Sokoban 的难度评估用"推箱状态图"（状态 = 箱子布局 + 人能到的区域，边 = 一次推），并发现可达局面数、子问题长度这类简单指标很有效；A* 搜索展开的节点数与人感觉的难度、人的步数高度相关。

### 8.2 第二层：设计者标注

机制种类和相互作用，每个 1–3 分；另有 `design_difficulty`（自评 1–5）。

### 8.3 第三层：真人校准

- 每个难度档放 5 个"锚点关"。
- 用新玩家的**中位通关时间、撤销次数、卡住次数**（超过 60 秒没进展）校准权重。
- 试玩记录表见附录 C。

### 8.4 输出与用途

- 每关 **1–5 星**（暂定档名：入门、熟悉、进阶、挑战、谜局）+ 一张"为什么难"的拆解（步数、机制数、诱饵、联动）。
- 用途：选关排序、章内难度单调上升、相邻关不教同一个发现（游戏仓库 `docs/design/level-quality.md` 第 3 节）。
- 多屏关拆开算：每屏一个分 + 屏间接口数（论文里的"问题分解"）。

### 8.5 上线顺序

先做"指标面板"（现有 `model-check` 的数据就能出第一版，用来看清 46 关的分布）→ 设计器接入 → 有 20–30 关真人数据后再合成总分。

## 9 地图风格与机制融合（IP × 玩法）

### 9.1 三条规则

1. **机制先行，皮肤后上**：先定这张图用哪几个机制，再选主题。同一机制可以有多个地区皮肤。
2. **皮肤要"说出规则"**：看起来脆的会塌，画着刻度的是收集斗，成对的用同一个符号。可建一套视觉语法（建议，须与已确认美术协调）：

   | 规则类 | 视觉倾向 |
   |---|---|
   | 一次性（桥塌、酸、引信、纸扎、冰融） | 易碎质感：裂纹、纸、蜡烛、薄冰 |
   | 可重复（石、铁、木架） | 厚重 |
   | 成对（门与压板、传送阵、桥与承重） | 同符号或同色 |
   | 因果相连（开关与门） | 可见的连线 |
   | 危险（酸、火、深坑） | 警示色 |

3. **规则和皮肤分两层**：设计器里主题是个下拉，换主题不改规则；发布前检查"这个机制在这个主题下有没有对应美术或占位"。
