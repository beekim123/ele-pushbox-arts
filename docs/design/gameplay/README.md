# 玩法设计 · 新关卡线梳理

状态：设计阶段（2026-10-23）。现在只做设计；实现以后在游戏仓库开新分支做。正文见 [关卡设计新方向（草案）](level-design-direction.md)。

## 一句话

关卡模式要重做：从"每关演示一个机制"，改成"有诱饵、有冲突、想通了才能过"的谜题。为此搭一条能反复用的生产线：机制卡 → 机制两两组合并加冲突 → 在 HTML 设计器里摆地图 → 求解器算有没有解、算难度 → 配上主题皮肤 → 真人试玩校准 → 导出 JSON → Godot 读取。

## 和现状的关系

游戏里关卡 v1 和配送 v1 都已冻结（游戏只保证第一关能玩，重做时清掉旧关卡）。草案第 1 节对旧关卡的诊断仍然成立，新关卡线是重做，不在旧关卡上改。

## 决定到哪一步了

| 程度 | 内容 |
|---|---|
| 已定 | 每关独立设计，三种形态（单屏、大地图、多屏联动）；HTML 设计器导出 JSON，Godot 直接读，JSON 提交进 git；机制只列清单，先不挑；设计文档放美术仓库、公开；关卡设计器放美术仓库工作台，等机制卡和操作方案定了再做 |
| 暂定（实机可能改） | 操作只留方向键 + 空格 + Z 撤销，一关最多 2 个工具；多屏联动用"几个单屏 + 信号"，不做超大物理世界 |
| 建议 | 难度分三层，先做指标面板；先定机制、再上皮肤，规则和皮肤分两层 |
| 待定 | 放游戏的哪个模块（以后开新分支时定）、候选机制选哪些、新关卡格式的字段、多屏关作者解怎么记、要不要 JSON Schema、难度权重和档名 |

## 每件事落在哪

| 要做的事 | 在哪做 |
|---|---|
| 设计原则、三种形态、机制卡、组合方法、难度方法 | 美术仓库 `docs/design/gameplay/`（本目录） |
| 新操作的按键提示、操作说明页、HUD 上的工具图标 | 美术仓库，先画 HTML 设计稿（等操作方案确认后再画） |
| 机制视觉语法（易碎、厚重、成对同符号、因果连线、危险警示） | 美术仓库，确认后写进美术规范 |
| 每个机制在每个主题下有没有美术 | 美术仓库 |
| 多屏切换时的镜头衔接 | 美术仓库，先出设计 |
| 新关卡格式（暂名 `pushbox.levelspec/2`）、Godot 加载器 | 游戏仓库，以后开新分支 |
| 关卡设计器（地图编辑器）、求解器、难度面板 | 美术仓库工作台，「关卡设计器」入口（用户 2026-10-23 决定，取代草案第 7.1 节的「游戏仓库作者页面」）。设计模型的 18 个机制插件和求解器从游戏仓库搬过来、公开，新关卡线的设计模型以美术仓库为准。**等机制卡和操作方案定了再做**（已预留 WB-17、WB-18） |

## 要先在美术 HTML 出设计的页面（界面清单「待设计」一组）

1. 新操作的按键提示（局内 HUD）
2. 新操作的操作说明页
3. 本关工具图标（最多 2 个，在 HUD 上）
4. 机制视觉语法样张

这 4 项都依赖暂定的操作方案和机制选择，先登记、不画；操作方案确认后再派美术包。

## 建议的顺序

| 步 | 做什么 | 依赖 |
|---|---|---|
| 1 | 36 个已实现机制的机制卡（纯文档）；难度指标面板第一版，先看清旧关卡的分布 | 无 |
| 2 | 操作方案用原型试一下（3 个新玩家不教就会） | 设计器或简易原型 |
| 3 | 美术 HTML：按键提示、操作说明、工具图标、视觉语法 | 第 2 步 |
| 4 | 美术仓库：设计模型和求解器搬过来（WB-17）；关卡设计器最小版：单屏的画、试玩、撤销、求解、SDK 提醒、导出 / 导入 JSON（WB-18） | 第 1、2 步（机制卡、操作方案）定了以后 |
| 4b | 游戏仓库：新关卡格式的 Godot 加载器 | 开新分支时 |
| 5 | 第一批约 12 关 → 3–5 人真人试玩 → 校准难度 | 第 4 步 |
| 6 | 多屏联动、皮肤配对检查 | 最后 |
