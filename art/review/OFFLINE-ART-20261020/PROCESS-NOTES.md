# 为什么做得慢（制作复盘）与流程改进建议

时间：02:34 开工，约 11:00 交付，82 项一次做完。像素绘制本身不是大头，时间主要花在界面（23 张 × 中英两版）和文字上。

## 慢在哪里

1. **每组界面都是整套手工活**：写画法（JS 模块）→ 写中英文字表 → 给新字补字形（font 模块）→ 宽度检查 → 渲染中英两版目检 → 再改。6 组界面 6 遍，每遍 3–5 轮。
2. **英文宽度反复缩短，需要多轮测量**：收件人规则行与小费标共用 221px；派人卡片名 78px；伙计详情 254px × 2 行；伙计加入面板 3 行；教学说明一屏放不下。每改一句都要重新渲染量宽。
3. **字体/排版坑，每个都要一轮排查**：
   - 自动换行会在撇号处断开；弯撇号「’」在字库里是全角宽 → 全部改直撇号。
   - 「−」（U+2212）字库缺字显示方框，但字形检查没报 → 改用「-」。
   - 按钮高 15px 会裁掉 12px 中文底部 → 统一 17px。
4. **大量新文案要现写**：道具 / 增益 / 心愿说明、12 位收件人 × 4 句故事英文、伙计人设与本事、教学说明，每句中英都要合宽度。
5. **读设计、定版式耗时**：每组要先读对应设计段落和旧样张，再决定面板尺寸和信息层级。
6. **工具流程与离线包不一致**：简报里的命令面向 git 仓库（改 art.mjs / index.html / tests），离线包要改为登记 `authoring-modules.json`；新模块不登记就不会被快速预览加载，查了一轮才发现。
7. **流水线小限制**：`make_sources` 要求字体文件先存在；依赖要每个 id 单独进程记录（同进程会串）；`build` 不能在中途跑（会把半成品记进去）；渲染日志有大量 qps 噪声要过滤。
8. **会话本身的开销**：上下文压缩后要重读代码找回细节；看图工具同一路径会缓存旧图，每次都要换文件名，否则看到的是旧样张。

## 改进建议

1. **给界面做模板**：面板、标题、键位条、按钮（固定 17px）、列表 + 详情两栏做成公用组件，一组界面只写差异部分。
2. **先定宽度预算再写文案**：简报里直接给每个文字槽的像素宽和行数（如“规则行 221px、1 行”），译文一次写到位；再加一个自动截字报告，列出每个键的实际宽度。
3. **字形检查加两条**：扫描非 ASCII 标点（弯引号、U+2212 等）直接报错；渲染结果里出现缺字方框也报错。
4. **文案与美术分开派**：故事 / 人设 / 说明这类长文案先由文案定稿（中英对照），美术只负责排版。
5. **离线包自带正确命令**：把“登记 authoring-modules.json”写进简报，删掉 git 仓库专用步骤；`make_sources` 自动生成缺失的空字体模块；依赖记录默认逐 id 隔离。
6. **一组一包、组内批量渲染**：变体样张一条命令批量渲染 + 自动拼图，减少逐张目检；看图用带时间戳的文件名。
